# Fork scope and upstream differences

This repository is Igloczek's fork of
[PiotrMachowski/lovelace-xiaomi-vacuum-map-card](https://github.com/PiotrMachowski/lovelace-xiaomi-vacuum-map-card),
published as **Better Xiaomi Vacuum Map Card**. Upstream is the baseline; this file records where the
fork behaves differently and how to sync upstream. Planned work is in [ROADMAP.md](ROADMAP.md),
released changes in [CHANGELOG.md](CHANGELOG.md).

## Compatibility

The card registers its own element (`custom:better-xiaomi-vacuum-map-card`) and keeps
`custom:xiaomi-vacuum-map-card` as an alias while the upstream bundle is not loaded, so an existing
dashboard keeps rendering and the fork can be installed next to the original card. The release
asset (`xiaomi-vacuum-map-card.js`) and every existing configuration key keep their upstream names
and meaning. The fork adds options; it does not rename or remove them.

## Active differences

Each row is a preservation criterion for an upstream import. The
[sync checklist](.agents/skills/sync-upstream/fork-differences.md) maps every row to the files that
implement it and the proof that must still pass.

| Area | Behaviour in this fork | Why |
| --- | --- | --- |
| <a id="persistent-map-view-and-rotation"></a>Persistent map view and rotation | Zoom, position and rotation are remembered per card, preset and map by default (`persist_map_view`), the lock state is remembered too (`persist_map_lock`), and two-finger rotation is on by default (`map_rotation_gesture`). A stored view records the map width its offsets were taken at, so reopening it at another width, and resizing the card while zoomed, keeps the same map point in view. | A dashboard should reopen the map where the user left it, on any screen. |
| <a id="rotation-controls"></a>Rotation controls | The toolbar has no manual rotate button; configured `map_rotation` and the rotation gesture remain available. | Rotation belongs in the gesture and the configuration, not a toolbar button. |
| <a id="automatic-room-mapping"></a>Automatic room mapping | Room outlines, names, label positions and hit targets are built from the camera's `rooms` metadata and the map's fill colours. Each room takes the solid colour patch that best fits its camera bounds, so rooms may share a colour (four-colour palettes); when two rooms of one colour have interlocking camera bounds (two L-shaped rooms around a hallway), the colour's connected patches are attributed to the rooms instead: a room keeps the patch that fills its bounds best, a piece a path or furniture cuts off a floor goes to the one room whose floor it reaches across a drawn-over colour and never across a wall, and the attribution is kept only when every room the plain trace found is still found and no room loses its own floor, so a map can never come out worse than the plain per-room trace (the differential suite scores both against a synthetic ground truth); the bounds of rooms that share its colour (the smaller one owning a nested overlap) are a barrier, gaps up to 8 px that paths draw over a room are closed, areas rooms enclose (robot, icons, furniture) go to the nearest room whose bounds contain them, and taps on non-background pixels reach a room within 10 px inside its bounds, never over another detected room's colour; undetected rooms' metadata shapes are never given to a detected room. A detection is reused for newer snapshots with the same room geometry, calibration and size (up to ten minutes when it found every room, one minute otherwise). Taps resolve through a per-pixel room map rather than the tapped colour, then through the outlines of undetected rooms (smallest first), which are not click targets of their own while a detection exists. Label points stay inside non-convex rooms, and unusable metadata entries are skipped; the click that ends a drag, pinch or rotate of the map is dropped (`src/model/tap-guard.ts`) so moving the map never selects a room; configured rooms remain the fallback when metadata or distinct colours are unavailable. | Hand-drawing room outlines is the main setup cost of the upstream card. |
| <a id="live-path"></a>Live path | `live_path` draws the robot (a dot with a heading chevron) and the path it drove over the map, a static floorplan image included, from a position attribute in vacuum coordinates (`vacuum_position` on the map camera by default; `{x, y, a}` or `[x, y, a]`). The card records the positions it sees while the vacuum is on a run (`src/model/live-path.ts`), starts a new path on the next run, keeps the last one after docking and stores it per vacuum and source in the browser. The track stays in vacuum coordinates and is converted with the current calibration on every render (`src/card/live-path.ts`), because a camera's pixel calibration moves between frames. | Integrations publish only the live position (Dreame paints the path into its own camera image), so a floorplan picture had no way to show where the robot is or has been (#47, upstream #503). |
| <a id="rotated-zones"></a>Rotated zones | `MANUAL_ROTATABLE_RECTANGLE` is a free-drawn zone with a rotate handle (snaps to whole degrees and onto multiples of 45° within 3°). The zone stays a true rectangle and is sent as its four corners, `[x1, y1, x2, y2, x3, y3, x4, y4]`, in the order the Viomi V8 robot gets a zone from `clean_zone` (`src/model/rotated-zone.ts`), so at 0° it sends what a plain zone sends. Only the Viomi templates offer it (`vacuum_clean_zone_rotatable`): tykarol's `viomi_vacuum_v8.clean_area`, and three raw `vacuum.send_command` steps (`set_uploadmap`, `set_zone`, `set_mode`) for miio2, viomise and al-one/hass-xiaomi-miot. For that, `service_call_schema` may be a list of calls, sent in order and stopped at the first failure. Every other platform keeps axis-aligned zones: their robots (Dreame, Roborock, every Valetudo backend) only take a box. | Walls at 45° cannot be followed by an axis-aligned zone (#49, upstream #134). The Viomi robot cleans any four corners it is given; its integrations' own zone services rebuild a box. |
| <a id="default-zone"></a>Default zone | A zone mode (`MANUAL_RECTANGLE`, `MANUAL_ROTATABLE_RECTANGLE`) opens with one zone on the map, a third of the visible map in size, once the map image is measured and the calibration is valid. `+` adds further zones up to `max_selections`. A fresh selection (opening the mode, a preset switch, `selection.clear`, a run with `clean_selection_on_start`) places it again; a rebuild keeps the user's zones, and a deleted zone stays deleted until the next fresh selection. | Upstream opens a zone mode with an empty map and a `+` to find first; the maintainer took that for a broken zone mode. One zone to drag is what most runs need, and the `+` stays for several zones. |
| <a id="zone-style"></a>Zone style | A drawn zone is a solid outline and a 25 % tint in the theme's primary colour over a halo in the card's background colour, and its label is the room pill (the zone's number as the badge, its size as the text) at the zone's centre. During a drag the outline, the halo and the label follow the zone without a render. | Upstream's white dashed outline, white fill and white text vanish on white floor, and the default zone made that the first thing on screen. |
| <a id="map-appearance"></a>Map appearance | `transparent_background` makes near-white pixels transparent for a dark dashboard. Every label on the map (rooms, predefined points, predefined rectangles) is one style, the pill of the [cleaning-order badges](#b5-cleaning-order-badges) (`MapObject.renderPill` in `src/model/map_objects/map-object.ts`): unselected it is the pill without a badge, selected it gains the badge (a room's number or a checkmark), so a tap changes the pill instead of swapping a plain text label for a different element. The pill is placed by a CSS transform on the SVG group around its `foreignObject`, never on its HTML (no position, transform or filter on the pill), because WebKit paints such HTML away from its layout box; `test/visual/paint.spec.ts` and the e2e `webkit` project prove it is painted in place. `map_source.room_labels: false` hides the card's room names for a map image that already names its rooms; a selected room keeps its badge. Every room outline is drawn before any room's icon, label or stale marker, so a label that reaches across a wall is never cut by the next room's border. | Upstream labels are hard to read on coloured maps, and plain text beside the selected pill gave the map two unrelated label styles. |
| <a id="zoom-alignment"></a>Zoom alignment | The base image scale comes from the canvas's untransformed layout width, so zoom and rotation apply once to the image and its overlays. | A transformed measurement applied the scale twice and detached the room overlays. |
| <a id="b6-map-refresh"></a>Map refresh policy | A pure policy (`src/model/map-refresh-policy.ts`) decides the camera snapshot's cache-buster: the URL changes on a camera `last_updated`/`entity_picture` change or about once per five seconds, and stays frozen while the tab is hidden. A camera change waits, for at most one interval, while the current snapshot is still loading, and the load fetches the newest state. A render the interval holds back schedules exactly one trailing refresh, cancelled on disconnect, and room-colour detection shares the same camera identity key and runs only on the snapshot that is shown, never on an older one the camera has moved past. | Upstream reloaded the snapshot on every vacuum, tile or icon update, and a camera faster than its download aborted every snapshot. |
| <a id="b2-editor-room-config"></a>Editor room-config path | Generating rooms copies the mode list instead of mutating Home Assistant's frozen configuration, scopes the room-config request and answer to the requesting card (entity, camera, request id), keeps exactly one ROOM mode across repeated generation, renders `ha-input` with an `ha-textfield` fallback, draws switch labels when the frontend has no `ha-formfield`, and removes an editor-preview card's listeners on disconnect, opens without `loadCardHelpers`, and tolerates a cleared camera field. | Upstream generation mutated the config, leaked across cards and lost its labels on newer frontends. |
| <a id="editor-picker-fallback"></a>Editor picker fallback | The entity, vacuum-platform and camera pickers render with `ha-select`, or with a native `<select>` styled from the theme's variables when the frontend does not define it; both paths show the configured value, write the same config key and fire the same `config-changed` event, and a `ha-select` defined after the first render replaces the fallback instead of the editor settling on it because the frontend had not loaded the element yet. | Home Assistant has removed editor elements before (`ha-formfield` in 2026.11); a removed or renamed `ha-select` left three empty boxes with no way to configure the card. |
| <a id="delayed-card-work"></a>Delayed card work | Delayed callbacks are tracked and cancelled in `disconnectedCallback`, a callback queued after removal does not start a timer, a map-image `load` that arrives after removal is replayed when the card is attached again, and a render while detached keeps the current camera snapshot instead of the disconnected placeholder. | Home Assistant re-layouts and re-attaches cards; upstream could leave a static map blank or animate a re-attached card. |
| <a id="release-packaging"></a>Release packaging | The release workflow has `contents: write`, attaches the built `xiaomi-vacuum-map-card.js`, and accepts an unchanged version (`npm version --allow-same-version`). | Without the permission the workflow cannot upload the asset, and a version already set in `package.json` must not block the release. |
| <a id="ci-validation"></a>CI validation | HACS validation runs every check including `issues`, because the fork tracks its own reports; there is no `dev` branch or master→dev automerge job, and build and visual checks target `master` only. | The default HACS setup would fail on the fork's own issue tracker. Every fork change lands on `master` directly, so upstream's `dev` mirror only duplicated CI runs and sent contributors to the wrong branch. |
| <a id="ci-baseline"></a>CI baseline | Build, release and HACS workflows use `actions/checkout@v7`; build and release run the Node version in `.nvmrc` (26, the current LTS) through `actions/setup-node@v7` with npm caching, and the build runs `npx tsc --noEmit` before bundling; `package-lock.json` is lockfile v3. | Upstream pins Node 14 and has no type-check gate. |
| <a id="oxc-toolchain"></a>Oxc toolchain | The bundle is built by Rolldown (`rolldown.config.mjs`), which resolves, transforms and minifies with Oxc and reads `experimentalDecorators` and `useDefineForClassFields: false` from `tsconfig.json`; `npm run lint` is oxlint (`.oxlintrc.json`); the whole code base is formatted with oxfmt (`.oxfmtrc.json`, embedded Lit templates left as written) and the build workflow checks it; and TypeScript 7 (the native compiler) is the type checker only. Dependencies are Lit 3, `custom-card-helpers` 2 and `home-assistant-js-websocket` 9; Lit subpaths are imported with their `.js` extension. | Upstream builds with Rollup 2, Babel, terser, ESLint 7 and TypeScript 4 from 2021. Without `useDefineForClassFields: false`, class fields would shadow Lit's reactive accessors and the card would never re-render. |
| <a id="latvian-translation"></a>Latvian translation | `lv.json` is registered, so `language: lv` and a Latvian Home Assistant get the Latvian strings; a test checks that every file in `src/localize/languages/` is registered. | Upstream ships `lv.json` and lists Latvian in the docs but never registers it, so Latvian users get English. |
| <a id="p0-test-infrastructure"></a>Test infrastructure | Vitest 5 with a happy-dom harness (`test/harness/`), fixture locations under `test/fixtures/`, `npm test` in CI, and a pure `RoomColorDetector.detectFromImageData` entry point. | Upstream has no unit-test harness. |
| <a id="b1-config-robustness"></a>Config robustness | An incomplete predefined room, calibration point or dynamic (entity-backed) selection reports a validation message and is skipped instead of throwing; valid entries behave as before. Every configuration value is shape-checked before use (mapping, list, known `selection_type`/`repeats_type`), so malformed YAML is reported by field name while an empty key (`null`, `""`) counts as absent, and `setConfig` resets the old-config and error state each time. An empty key is normalised away before validation and before rendering (`src/config-normalization.ts`), at every level, so `icons:`, `id:` or `map:` is treated exactly like an unwritten key and no field reaches the card as `null`; a `null` list item stays a broken entry and is reported, and user data (`data`, `variables`, `service_data`, `target`, translations, icon maps) is left as written; an explicit `label: ""` or `icon: ""` still means none. | Small configuration mistakes crashed the upstream card. |
| <a id="b7-registry-cache"></a>Registry lookup and caching | `getAllEntitiesFromTheSameDevice` reads the vacuum's `device_id` and makes one `config/entity_registry/get_entries` call for that device, memoized per connection, display registry and device entity set, with `/list` plus per-entry `/get` only as a fallback. The per-connection memo keeps only the most recent lookups, so a long-lived page does not retain one entry per registry update, and a lookup that fails on both paths is not cached. | Upstream downloaded the whole registry and fetched every entry on every `setConfig`, and an unbounded memo would leak on a wall tablet. |
| <a id="registry-renames"></a>Registry renames | The card re-renders when Home Assistant's naming inputs change identity (`hass.formatEntityName`, `hass.entities`, `hass.devices`, `hass.areas`, `hass.floors`; `src/card/registry.ts`) and regenerates the current preset's generated icons and tiles, so an entity, device, area or floor rename and a registry icon reach the tiles without a reload; only the registry entries the preset's device and watched entities read are compared, so an unrelated registry update does not regenerate it, the newest refresh wins when two overlap, a refresh whose preset config was replaced by `setConfig` is dropped, and a lookup that fails on both websocket paths keeps the previous icons and tiles for the next registry change to retry; the registry lookup memoizes per display-registry object, so a registry update is a cache miss while a state-only update still hits it. | A rename writes no entity state and the generated tiles and icons store the label and icon resolved at generation time, so both stayed stale until the page was reloaded. |
| <a id="b3-tiles-labels-icons"></a>Tile labels, translations, durations and icons | Tile translations match case-insensitively, labels use `hass.formatEntityName` only where it exists with the current signature (2026.4+) and fall back to `friendly_name` then the entity id, `duration_unit` follows the sensor's unit (the template `multiplier` is the fallback for a unit-less sensor; Xiaomi Miio, humbertogontijo Roborock, Hypfer Valetudo, Deebot and Neatsvor declare it), Deebot's total time is `total_cleaning_time`, a non-numeric value of a numeric tile is shown without the unit, numbers use the user's number format, a missing `icon_source` or condition entity is tolerated, a `null` value in a tile config (a registry entry without an icon of its own) is skipped by the template replacer instead of rejecting the whole tile list, and `return_to_base` uses `mdi:home-import-outline`. | Upstream labels, durations and icons were wrong on some integrations, the 2025.10 helper signature threw during render, and one icon-less registry entry left a card without tiles. |
| <a id="b11-generated-defaults"></a>Generated defaults | `getStubConfig`/`generateConfig` take `vacuum_platform` from the vacuum's integration and the map from its own device; a preset without `map_modes` gets the platform's room mode when the camera publishes `rooms` and that template sends a complete call with room ids (not for name-based Neato, MyNeato, Wyze), and the mode is only added, never removed, so a briefly unavailable camera keeps the selection; camera `rooms` metadata is read through one defensive reader (`readCameraRooms`, mapping or list, numeric strings, broken entries skipped). | Upstream gave every vacuum Xiaomi Miio and any calibrated camera, left several platforms with no mode to select, and crashed on a broken room entry. |
| <a id="b5-cleaning-order-badges"></a>Cleaning-order badges | A selected room's label becomes a pill in the Xiaomi Home app style (a round badge plus the room name, centred exactly where the unselected label pill is, label offset included; the icon until selected, the badge alone without a name): the badge shows the room's position in click order where the mode's platform follows the order (`cleaning_order`, set in the Valetudo, ValetudoRE and roomba_plus templates) and a checkmark elsewhere. The pill's colours come from the theme (`--map-card-room-pill-*`) and are corrected to at least 4.5:1 for the name and the badge glyph (`src/model/room-pill-palette.ts`), it is set apart from the map by a soft shadow and a hairline from its text colour, the badge is the primary colour deepened under a white glyph, stays upright and the same size at any zoom and rotation, ignores pointer events, is drawn in a `foreignObject` whose box covers the map and half of it again on every side (WebKit repaints only that box, so a smaller one left an overlapping pill on screen after deselection), and never carries a badge on a stale room (its badge-less name pill is painted under the `!` marker). The remaining badges renumber on deselection, a room rebuild after a camera refresh keeps the click order, and the started run, stored once Home Assistant accepts the call (with the vacuum state shown when the call went out as its baseline), stays highlighted in the selection style. The run is stored per vacuum in the browser, read on every update and shared by the cards and tabs of that browser, and bound to its ROOM mode and its map (the preset's camera entity or image, plus the map id attribute the camera reports, if any, so a preset per floor neither shows nor locks another floor's run; runs stored without a map match any map); rooms are locked only while the vacuum reports `cleaning`/`returning` after the start (only a `cleaning` with a new `last_changed` or a different state than at Start counts; attribute-only updates do not), `unavailable`/`unknown` keep the run unlocked, and it ends when the vacuum leaves `cleaning`/`paused`/`returning`, three minutes without a start or 12 hours, on its own timer. While the start is pending and no new state has been reported, icon conditions read the vacuum as `cleaning`. | The order is sent to the platform but was invisible before cleaning started, and vanished when it did; numbers on a vacuum that plans its own route promised an order it does not keep, and polling integrations lag and drop out mid-run. The pill reads as selected at a glance, as in the vendor app, without the vendor app's unreadable dark-on-dark text. Multi-floor vacuums reuse segment ids on every map, so a run bound only to its mode locked every floor and highlighted the wrong rooms. |
| <a id="selection-lifetime"></a>Selection lifetime | Rebuilding the selectable rooms, zones and points (a `state_entity` or zone/point source change, a camera refresh, a change of the camera's room ids, the same preset's config set again) keeps the user's selection and its order: items are matched by room id, zone list or point position (`src/model/selection-rebuild.ts`), a vanished item drops out, a new item (or one whose `default_state` changed) gets its default, a `state_entity` item follows its entity, items from an unavailable source (camera `rooms`, zone/point entity) are held and restored in place, and `max_selections` keeps the first items. Manual shapes and the current preset and mode survive a config re-set. Only a mode or preset switch, the clear action and a run with `clean_selection_on_start` start afresh. | Upstream rebuilt from scratch on these paths, so an automation, a re-render or a refresh silently dropped, re-added or reordered what the user had selected. |
| <a id="templated-service-calls"></a>Templated service calls | With `evaluate_data_as_template`, the Jinja code inside `{{ }}` and `{% %}` is JSON-unescaped back to the code the user wrote before rendering, so a string room id from `[[selection]]` works bare and inside a quoted string (`'[[selection]]' \| from_json`); the render asks Home Assistant to report errors, settles on the first answer, unsubscribes and times out after 10 s; a failed render shows the failure toast, sends nothing and keeps the selection. | Metadata room ids are strings, so `{{ [[selection]] \| length }}` became a Jinja syntax error and the run button silently did nothing; upstream also sent the unevaluated template on a parse failure. |
| <a id="service-call-reporting"></a>Service-call reporting | Every service call the card makes (run button, preset activation, `state_entity` toggle, icon and tile actions) goes through `callServiceReported`, which turns off Home Assistant's own notification (`notifyOnError`) and shows one failure toast, with Home Assistant's translated message, on a rejection or a synchronous throw. The run button keeps the selection until Home Assistant accepts the call, and from the first tap until the answer (including a template render) a second tap shows "Already sending"; a run while the preset's vacuum is `unavailable` (offline, a dead battery after a failed dock) sends nothing and says so, because Home Assistant skips an unavailable entity without an error and the run would otherwise report success and show a run that never started (holding the button to show the call still works); `perform-action` icon and tile actions are sent as `call-service`, and the legacy `service_data` key is passed on as `data`, the only key `custom-card-helpers` 2 sends. | Upstream cleared the selection before the answer and sent the other calls without listening for one. |
| <a id="run-feedback"></a>Run feedback | The run button answers on itself: a spinner while the call is out, then a check on the theme's success colour or a cross on its error colour for 2 s (`--map-card-run-success-color`, `--map-card-run-failure-color`). Messages (a refusal, a failure with Home Assistant's reason, the editor's "copied") go to Home Assistant's own notification (`hass-notification`, shown on the screen, a failure for 8 s and dismissable); an accepted run sends no message, the button shows it, and takes back the card's own failure message still on screen (each card's messages carry their own `id`, closed with `duration: 0`; nothing is sent once that message has expired, because a frontend without ids would close whatever is on screen). Outside Home Assistant (no `<home-assistant>` ancestor) the card's own toast is kept. | Upstream's toast sits at the bottom of the card, out of sight on a tall card or a scrolled dashboard, far from the button that was tapped. |
| <a id="platform-payloads"></a>Platform payloads | A contract matrix checks every platform template × map mode × string/number room id against the integration's service schema, rendering templated modes in a real Home Assistant. Fork template fixes: setup platforms send `message`/`title` to `persistent_notification.create`; Hypfer Valetudo's predefined go-to sends numbers; Deebot sends `rooms`/`coordinates` as lists from Home Assistant 2026.3 and as comma-separated strings before (`legacy_service_call_schemas`, chosen from `hass.config.version`), with `id_type: number`; `send_command` rooms use `id_type: number`. `id_type: string` stringifies ids, and `[[point_x]]`/`[[point_y]]` work with `INTERNAL` repeats. | Upstream templates sent payloads these services reject or misread; no test checked them against the integrations. |
| <a id="b8-stale-room-selections"></a>Stale ROOM selections | Configured ROOM ids missing from the live camera `rooms` metadata are stale: drawn from their stored outline, marked red with a `!`, unselectable and pointer-transparent, named in a `hui-warning`, and dropped from `_getSelection` so they cannot reach a service call. A selected room whose id leaves the metadata is stale at once, without waiting for a rebuild (a selected room in a template-only mode has no configured id for the stale audit); while the whole selection would send nothing, that room stays on the map as a stale marker (`unavailableRooms`), a second `hui-warning` names it, and the run button refuses with a toast instead of sending an empty room list. Picking a usable room drops the marker, and a room whose id comes back within the same camera is restored to the selection in its place. Missing metadata means "unknown", not "all stale", and the configured rooms remain the fallback. The warning's message is a block of its own that wraps, because Home Assistant's alert lays its slot out on one line and cut the sentence after the first id in a narrow card. The `!` is sized and placed by the stylesheet: the card hands it only the room's geometry - the free space from the label point to the outline along each screen direction, traced through the outline polygon at the current map rotation, in map units - and CSS picks the placement from it with `min()`/`max()`. Its size and every clearance are expressions of the pill's own variables (`--map-card-internal-room-label-font-size` divided by `--map-scale`), so a theme font in `px`, `rem`, `em`, `vw` or `calc()` and a live theme change reach the marker with no card render and no computed-style read, and the marker reuses the shared label transform instead of repeating it. It is placed above the pill and clear of it while the room has that much space; otherwise it moves to the pill's badge side above the pill's name, and, where the room has no space above at all, the same clearance below the pill, which is what keeps a room at the image's top edge from clipping it. The name is the one clearance proved vertically rather than horizontally, because the pill is as wide as its text and no element's CSS can measure another's; a room too short for that keeps the marker on the pill's side, never over the name, and a room too small for the marker leaves it over the pill's edge, painted after the live rooms. | A re-map renumbers segments, so a stale selection could clean the wrong room; and a card that looks ready while the service call carries no room ids is a silent failure. |
| <a id="b9-default-map-view"></a>Default map view and reset | `map_view: {scale, x, y, rotation}` sets the opening view, and the reset control and `map_view.reset` action return to it; partial values fill from the neutral view, invalid values are reported, and the order is stored view, configured default, neutral. It applies at the start of a card or preset session and is ignored in `additional_presets`. A reset that arrives while the card has no layout box (a hidden dashboard view, a closed container) waits for the first real layout and then applies and stores the centred default, never a view computed from zero size. | Upstream always opened at the neutral view and had no reset to a configured one. |
| <a id="b10-horizontal-layout"></a>Horizontal layout and sections-view sizing | `layout: vertical \| horizontal` puts the map beside the controls when horizontal, with a clamped controls column that wraps and scrolls. The card is an inline-size container, so the stacked arrangement follows the card's width rather than the window's; `contain-intrinsic-inline-size` keeps a card in a shrink-to-fit parent (inline-block, a flex item, `fit-content`, card-mod centring) from collapsing to 0 px. Below a 400 px card width (`HORIZONTAL_STACK_BREAKPOINT_PX` in `src/card/styles.ts`) the container query stacks the map above the full-width controls, because the clamped column left the map 191 px wide and the controls a 114 px scroll window at the narrowest sections span; a narrow sidebar or popup stacks too. The stacked arrangement is accepted to start below the fold of a short sections cell (the default 6 rows), so the controls need a scroll inside the card until `grid_options.rows` is raised. `getGridOptions()` keeps the upstream default for vertical and asks for 6 rows and `min_columns: 9` for horizontal; it deliberately returns no `min_rows`/`max_rows`, so the height a user sets with Home Assistant's own `grid_options` (the sections resize handle) is never clamped. Side by side, a taller cell is filled by the controls column instead of leaving dead space below the map; stacked, the content keeps its natural height. A cell shorter than the content scrolls inside the card rather than overflowing, and a `ResizeObserver` recalculates the base scale after a resize, including across the stack. | Getting this layout needed `card-mod`, fixed-height sections cells overflowed, and the card's own minimum rows silently overrode the resize handle. |

## Upstream sync preservation contract

Every row in **Active differences** is a preservation criterion for an upstream import, including changes that merge without conflicts. Before syncing, follow [.agents/skills/sync-upstream/SKILL.md](.agents/skills/sync-upstream/SKILL.md); the checklist in [.agents/skills/sync-upstream/fork-differences.md](.agents/skills/sync-upstream/fork-differences.md) maps each area to the files that implement it and the test that proves it.

- Reconcile upstream improvements at the affected boundary; do not freeze an old implementation.
- Never resolve a conflict by choosing one side wholesale. Keep the fork behavior and reapply the upstream change around it.
- Never delete a fork regression test, a FORK.md row, a documentation anchor or the sync skill to make an import pass.
- If upstream now provides the same behavior, prove equivalence with the tests, then move the row to **Superseded differences** and record the upstream commit.
- Keep the upstream snapshot and this section current in the same pull request as the sync.

## Syncing upstream

This checkout has an `upstream` remote. In a fresh clone:

```sh
git remote add upstream https://github.com/PiotrMachowski/lovelace-xiaomi-vacuum-map-card.git
```

Follow [the sync skill](.agents/skills/sync-upstream/SKILL.md) for the full procedure. Before
merging, review both sides:

```sh
git fetch upstream
git log --left-right --cherry-pick --oneline upstream/master...master
git diff --stat upstream/master...master
```

Run the proof for every area the import touches, keep the fork behavior that still fits, and update
this file in the same pull request: the snapshot, the active rows, and any row that upstream has
superseded.
